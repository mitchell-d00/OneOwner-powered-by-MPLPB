# OneOwner and Combined MPLPB: separate applications

**Only the OneOwner repository is changed by this product work.** Combined MPLPB retains its own research application and its own existing website.

OneOwner is a separate **full-page** product with its own layout, identity, navigation and responsive styles. It does not expose the original research UI to the user. A generated OneOwner HTML artifact carries the unchanged original Python/WASM engine and `window.MPLPB` API so its ledger, reader, provenance gate, supersession and local persistence keep operating exactly as before.

```text
OneOwner full-page UI (product only)
  -> oneowner/adapter.js (fail-closed display and input validation)
     -> original window.MPLPB page-local JavaScript API
       -> unchanged Python engine (pinned research commit)
         -> original ledger, seals, gate, reader and supersession
```

An engine response becomes **SOURCE SUPPORTED** only after the original strict supported query returns `kind === "return"`, an actual citation and page hash, and `answer_supported !== false`. No answer from candidates, gate retrieval, synthetic interpretation, ambiguity or refusal is upgraded. The raw original decision remains available for inspection, not as a substitute proof.

The product page is generated by `scripts/build_oneowner.py` from the original research standalone WASM HTML. Original HTML nodes and scripts remain in the product artifact but the default original research controls are visually hidden; the new page is appended independently. No source bytes in the research checkout are changed. The packaged Python desktop copy has only its **presentation index.html** adapted. The actual upstream repository and Pages deployment remain untouched.

The browser source import requires the original API's genuine HTTPS source URL plus supplied text. It does not perform a fetch, claim verified authorship, treat a hash as truth, or rewrite a previous page. An unsupported URL-free original note must use the existing Python CLI `write`/`revise` or await a separately reviewed engine API.

## Release

The `oneowner-validation.yml` workflow validates the pinned engine and product including tests from the extracted ZIP. After a successful **main** run, only OneOwner's `oneowner-pages.yml` publishes that exact tested HTML artifact to the **OneOwner** website. The research site is not modified or redeployed. Candidate validation and deployed verification are distinct gates.

See [PRODUCT_SITE](PRODUCT_SITE.md) and [ROADMAP](ROADMAP.md).

## Conversation extensions

`oneowner/discovery.js` handles UI actions, native Wikipedia result normalization,
explicit-consent requests to a configured assistant service, and unsealed local
drafts. `chat.js` sends numbered choices and native follow-ups back to `api.chat`.
Product guide steps are interface guidance, not engine evidence or a second reader.
AI output ignores all provider claims of citations, support and tool actions;
only its message text is rendered, always with `answer_supported:false`.
The companion Python service holds provider credentials and cannot access the
ledger. Search excerpts are not automatically imported. General-web capture still
uses the native source bridge, while Wikipedia imports retain the native revision
capture path. All user and provider strings use `textContent`.

Native labels are disclosed in a compact Engine labels panel; exact metadata is
retained. Product guidance and AI activity are explicitly outside the native
transcript chain. Drafts use separate collection-scoped browser keys, not engine
storage. Full URL-free sealed browser authoring remains deferred; draft storage
does not pretend to implement that absent engine API.
